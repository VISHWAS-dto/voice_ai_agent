PHASE 2 - Audio ingestion (DONE)
================================

In one line:
Wrote the code that takes any audio clip and turns it into a clean,
standard format the model can read, plus a check for how much of the
clip is actual speech.

A bit more detail (app/audio/ingest.py):
- normalize_audio(bytes): feeds the raw audio (mp3, wav, m4a, or phone
  formats like 8kHz mu-law) through ffmpeg and gets back a 16kHz mono
  waveform. Everything happens in memory via pipes - nothing is ever
  saved to disk (the audio can contain private customer info).
  Throws a clear AudioDecodeError if the input is empty or corrupt.
- run_vad(waveform): uses webrtcvad to measure speech vs silence and
  returns total length, speech length, speech ratio (0-1), and how many
  separate speech chunks there are. Short or silent clips return a
  ratio of 0.0 instead of crashing.
  (webrtcvad picked over silero-vad: no model download, no torch, fast
  and predictable - it's just a rough "is there enough speech?" gate.)
- Pure, testable functions only - no API/route code, no global state.

Also added scripts/test_ingest.py: a manual test that runs a sample WAV
through both functions and prints the stats, and checks that silent /
empty / corrupt buffers are handled gracefully.

Note: needs the `ffmpeg` binary installed (brew install ffmpeg), and
`setuptools<81` in the venv (webrtcvad still imports the old
pkg_resources).

In Short 

1. Take the audio (mp3, wav, m4a, phone formats) → convert to the one standard format the model reads.
2. Check how much of it is actual speech (not silence/noise)

Next steps (not done yet):
- Fill in the quality-check code (app/audio/quality.py).
- Wire up the POST /analyze endpoint and the websocket.

PHASE 3 - Model inference wrapper (DONE)
=======================================

In one line:
Wrote the code that actually runs the ML model on a cleaned-up waveform
and turns its raw numbers into "male/female + age bracket + how sure".

A bit more detail (app/inference/model.py):
- AttributeInferencer class:
  * __init__ loads "audeering/wav2vec2-large-robust-24-ft-age-gender"
    once, on startup, into .model_cache/ (~1.3 GB). Fails fast with a
    clear RuntimeError if the model can't load, rather than per request.
  * predict(waveform, sample_rate=16000) -> dict with:
      gender_prediction  : "male" | "female" | "unknown"
      gender_confidence  : 0-1 (the softmax prob of the reported class)
      age_bracket        : "18-30" | "31-45" | "46-60" | "60+" | "unknown"
      age_confidence     : 0-1 (a modest heuristic, see below)
      inference_ms       : time in the model forward pass ONLY
                           (preprocessing + bucket mapping excluded)
  * The class holds only the model weights across calls - nothing
    per-request is cached.
- Why this model: the backbone (wav2vec2-large-ROBUST) was pre-trained
  on messy audio including telephone speech (Switchboard/Fisher), so it
  holds up on 8 kHz G.711 call-center audio, codec noise and cross-talk
  far better than a clean-studio model. One forward pass, two heads
  (age regression + 3-class gender) = both attributes cheaply.
- Gender: the model has a 3rd class, "child". We map a child-dominant
  prediction (and any malformed output) to "unknown" - the API has no
  "child" value and the child probability is not a male/female
  confidence, so we don't surface it.
- Age bucketing: the age head is a regression (value * 100 = years). We
  bucket by predicted year using the brackets' own edges (boundary year
  falls in the lower bracket: 30 -> "18-30"). Predicted age < 18 ->
  "unknown" (we only score adult callers). age_confidence has no real
  posterior behind it, so it's a deliberately capped proxy (~0.30 on a
  bracket edge, ~0.65 dead-centre, never near 1.0) for "how interior to
  the bucket is the estimate" - silence regresses mid-bracket and must
  not read as confident.
- The whole forward pass is wrapped in try/except: on ANY failure it
  returns "unknown"/0.0 for both fields instead of crashing.

Also:
- scripts/test_inference.py: loads AttributeInferencer once, runs
  predict() on sample.wav (prints full dict + total time), then on a
  synthetic 3 s silent buffer (confirms no crash + low-confidence
  /unknown output).
- Fixed a transformers-5 incompat in both the model wrapper and
  scripts/test_model_load.py: the audeering model card calls the legacy
  self.init_weights(); on transformers >= 5 that skips setup
  from_pretrained needs, so use self.post_init() instead.

PHASE 4 - Quality gate + real /analyze endpoint (DONE)
=====================================================

In one line:
Wrote the "is this clip good enough?" check and connected all the pieces
into a working POST /analyze endpoint.

A bit more detail:
- app/audio/quality.py: assess_quality(vad_stats) looks at how much of
  the clip is speech and returns one of:
    * "good"         - at least half the clip is speech
    * "degraded"     - some speech (15-50%), likely noisy/intermittent
    * "insufficient" - almost no speech, or clip shorter than 0.5s
  Thresholds are a hand-picked starting point, not tuned on labeled
  data yet (noted as a limitation in the README).
- app/api/routes.py: POST /analyze now actually works:
    1. Reads the uploaded file into memory - never saved to disk.
    2. Makes a fresh contact_id (uuid) per request.
    3. Decodes the audio; if it's corrupt/empty, returns
       "insufficient" + unknown instead of an error.
    4. Runs VAD + quality check.
    5. If "insufficient", skips the model entirely (saves compute,
       avoids confident guesses on silence).
    6. Otherwise runs the model.
    7. Times the whole thing (not just the model).
    8. Wrapped in a catch-all: ANY unexpected error still returns a
       200 with all-unknown fields, never a 500 - this is a soft
       signal that must not break the caller.
    9. Logs contact_id, quality, timing, predictions - NEVER the audio.
- app/main.py: loads the model ONCE at startup (FastAPI lifespan) and
  reuses it for every request, so no multi-second cold start per call.
- tests/test_analyze.py: uploads sample.wav and checks the response
  shape/values; uploads a corrupt file and an empty file and checks
  both come back as "insufficient" gracefully (no 500). All pass.

The service is now end-to-end functional: upload audio -> get back
gender + age bracket + confidence + quality rating.

PHASE 5 - Reliability, Observability & Dockerization (DONE)
==========================================================

In one line:
Made the service tough enough to ship: it never crashes the caller, it
never hangs, it writes clean logs you can search, and it now runs the
same way inside a container as it does on a laptop.

Think of it like this:
Phases 1-4 built a working machine. Phase 5 bolts on the seatbelts, the
dashboard warning lights, and puts the whole thing in a shipping crate
so it arrives in one piece anywhere.

------------------------------------------------------------------
PART A - Reliability ("it must not break the thing calling it")
------------------------------------------------------------------

This service is a *helper* for a live voice AI system. If our helper
falls over, the phone call must NOT fall over with it. So:

1. Never returns an error.
   No matter what goes wrong inside - a bad audio file, a bug, the model
   choking - the service still answers politely with "I don't know"
   (gender = unknown, age = unknown, quality = "insufficient"). The
   caller gets a normal, usable answer every single time.

2. Never hangs.
   We put a 3-second stopwatch on the whole process. If analysing a clip
   somehow takes longer than that, we stop waiting and immediately send
   back an "I don't know" answer instead of leaving the caller hanging
   on the line. (The slow work quietly finishes in the background and is
   thrown away.)

3. The model is loaded ONCE, at startup - confirmed.
   The AI model is about 1.3 GB and takes a few seconds to load. We load
   it a single time when the service boots up, then reuse it for every
   request. We double-checked the earlier "3.4 seconds on the first
   call" worry: that delay was the service *starting up*, not something
   that happens on every call. Normal calls take a few hundred
   milliseconds.

4. New "/health" check.
   A simple address the container system can ping to ask "are you alive,
   and is your model ready?" It answers:
     {"status": "ok", "model_loaded": true}
   This is what lets the system know it's safe to start sending real
   traffic. (The old "/healthz" name still works too.)

------------------------------------------------------------------
PART B - Observability ("we need to see what it's doing")
------------------------------------------------------------------

Every time the service analyses a clip, it now writes ONE tidy line to
its log - formatted as JSON, so tools can search and chart it easily.

Each line records:
  - contact_id  (a random ID for that one request)
  - audio_quality  (good / degraded / insufficient)
  - the predicted gender and age bracket
  - how many milliseconds it took
  - the outcome: "ok", "degraded", or "error_fallback"

The log line's loudness matches the situation:
  - INFO     = normal, healthy request
  - WARNING  = the audio was poor, or a clip was skipped / timed out
  - ERROR    = something unexpected went wrong and we fell back to
               "I don't know"

Privacy: the logs NEVER contain the actual audio, the uploaded file's
name, or anything else about the caller. The only identifier is the
random contact_id we generate ourselves. (We wrote a test that
specifically checks a nosy filename like "caller-jane-doe-ssn-123.wav"
never leaks into the logs.)

------------------------------------------------------------------
PART C - Dockerize ("put it in a shipping crate")
------------------------------------------------------------------

A "container" is a sealed box that holds the app plus everything it
needs, so it runs identically on any machine.

The Dockerfile (the recipe for that box):
  - Starts from a small standard Python base.
  - Installs ffmpeg - the audio-conversion tool. It's a system program,
    not something pip can install, so we install it separately.
  - Installs the Python packages from requirements.txt.
  - Copies in our app code.
  - Downloads the 1.3 GB AI model *while the box is being built* and
    bakes it in.
      Why: the box then starts up instantly and works even with no
      internet. The trade-off is a bigger box and a slower one-time
      build. The alternative - downloading the model the first time it
      runs - makes that first phone call wait several seconds and fails
      completely if the machine has no internet. We chose reliability.
      (This reasoning is written in a comment in the file.)
  - Opens port 8000 and starts the web server.

docker-compose.yml (the one-command way to run it):
  - Builds the box from the Dockerfile.
  - Connects port 8000 so you can reach it.
  - Attaches a persistent storage area for the model, so restarting the
    container doesn't re-download 1.3 GB every time.
  - Adds a health check that pings "/health" - the container only counts
    as "healthy" once the model has finished loading.

Supporting files: a small startup script (docker-entrypoint.sh) that
copies the baked-in model into the persistent storage on first run, and
a .dockerignore file so junk (the local Python environment, the git
history) doesn't get packed into the box.

------------------------------------------------------------------
PART D - How to test the whole thing from scratch
------------------------------------------------------------------

The exact commands are in the chat / README, but the shape of it:
  1. Wipe everything (old box, old container, saved model).
  2. Rebuild the box from zero with no shortcuts.
  3. Start it and wait for it to report "healthy".
  4. Check the startup logs say the model loaded exactly once.
  5. Hit "/health" - expect model_loaded: true.
  6. Upload sample.wav to "/analyze" - expect the same answer the
     laptop version gives.
  7. Upload a corrupt file - expect a polite "insufficient / unknown",
     NOT an error.
  8. Check the log line is clean JSON with no filename in it.
  9. Open the Swagger page (http://localhost:8000/docs) and try it
     there too.
 10. Restart the container - confirm it does NOT re-download the model.

PHASE 6 - Tests + Eval harness (DONE)
====================================

In one line:
Wrote the tests that prove each piece behaves, and a small honest
"report card" script that scores the model on labeled clips.

Think of it like this:
Phases 1-5 built and hardened the machine. Phase 6 is the inspection:
a checklist that each part passes (unit + integration tests) and a
one-page report on how well the AI actually guesses (the eval harness).

------------------------------------------------------------------
PART A - Unit tests for the quality gate (tests/test_quality.py)
------------------------------------------------------------------

The "is this clip good enough?" function (assess_quality) has a few
simple rules. These 27 tiny tests check every rule and, importantly,
every exact edge:

  - lots of speech (>= 50% of the clip)      -> "good"
  - some speech (15% - 50%)                  -> "degraded"
  - almost no speech (< 15%)                 -> "insufficient"
  - clip shorter than 0.5 seconds           -> "insufficient"
                                               (no matter how much speech)
  - less than 0.5s of actual speech          -> "insufficient"

We pin the exact boundary behaviour (exactly 0.15 and exactly 0.5) so
that if someone later retunes those numbers, a test lights up and it's
a deliberate change, not an accident. Also checks the function doesn't
crash on a broken/empty input.

------------------------------------------------------------------
PART B - Integration tests for the API (tests/test_analyze.py)
------------------------------------------------------------------

These start the real app (real model loaded once) and poke it like a
real caller would:

  1. Upload sample.wav -> expect HTTP 200, and a response that has all
     the right fields: a valid random ID (uuid4), a gender that is
     male / female / unknown, an age bracket that is one of the four
     buckets or unknown, confidence numbers that are real decimals
     between 0 and 1, and a processing time. Also: every request gets
     its OWN fresh ID.
  2. Upload a corrupt file, then an empty file -> expect HTTP 200
     (NOT a 500 error), quality = "insufficient", gender/age = unknown.
     The service must degrade politely, never blow up on the caller.
  3. GET /health -> expect 200 with model_loaded: true.

Note: the upload field is named "audio" (not "file").

------------------------------------------------------------------
PART C - Eval harness (eval/run_eval.py)
------------------------------------------------------------------

What it does:
  - Reads a list of labeled clips (eval/datasets/manifest.csv): each row
    is a file path + the true gender + true age bracket.
  - Runs each clip straight through the model (not the web API - we're
    testing the model, not FastAPI).
  - Prints a small report:
      * gender accuracy - % it got right, counting only the clips where
        it actually committed to male/female. How often it said
        "unknown" is reported SEPARATELY (an "I don't know" is not a
        wrong answer and not a right one).
      * age-bracket accuracy - same idea, exact bracket match.
      * a calibration check - it groups predictions by the confidence
        the model reported (0.5-0.6, 0.6-0.7, ...) and shows the real
        hit-rate in each group. If it says "0.9 confident" a lot but is
        only right 60% of the time, the confidence number is not
        trustworthy - this table is where you'd see that.
  - One bad/missing/corrupt clip is logged and skipped - it never
    crashes the whole run.
  - Optional: --json dumps the raw per-clip results.

HONEST limitations (say these out loud in the README / video):
  - It's a STUB eval on a TINY hand-picked set. As shipped it has ONE
    clip (sample.wav). Even at 10-20 clips it's an anecdote, not a real
    benchmark - the error bars on an accuracy from ~15 samples are
    roughly +/- 25 points.
  - No class balance: 12 men + 2 women would let a "always male" model
    score 86% and teach us nothing.
  - The bundled label is unverified (marked verified=no) - sample.wav
    is widely cited as a male speaker but not independently checked, and
    the speaker's age is unpublished so the bracket is a guess. The
    report shows "verified-only" numbers separately for this reason.
  - Why not Mozilla Common Voice out of the box? Every current version
    is a GATED dataset on Hugging Face now - needs an account, a token,
    an accepted licence, the `datasets` library, and a multi-GB
    download. Deliberately NOT wired in so the script runs with zero
    setup. `python eval/run_eval.py --help` prints the ~15 lines to
    extend it from Common Voice if you have a token (and a warning that
    CV's self-reported labels skew young + male).

What we saw on the one bundled clip: the model returned gender=unknown
(its internal "child" class won) and age=18-30 for a ~46-year-old male
TIMIT speaker - a concrete example of it struggling on short, 16 kHz,
telephone-ish audio. Exactly the kind of thing a real eval set would
quantify.
